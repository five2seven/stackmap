# StackMap v1.1.3 Portainer Docker Port-Summary Compatibility Plan

**Plan status:** Complete. The single patch implementation task is Complete; no additional task exists. This closeout does not tag or release v1.1.3, publish GHCR, or deploy Pages.

## Objective and fixed boundary

StackMap v1.1.3 will correct preview decoding for valid Docker container-list port summaries representing unpublished ports. The real Portainer response contains entries such as `{ "PrivatePort": 2442, "PublicPort": null, "Type": "tcp" }`, with `IP` omitted. Portainer connection and environment discovery succeed, but the current strict projection rejects that valid response before preview mapping.

The fix is limited to Docker Engine API port-summary semantics. SQLite remains the sole production authority, and the existing manual discovery, preview, explicitly confirmed create-only import, provenance, credential protections, network policy, and demo boundary remain unchanged.

## Confirmed incompatibility and API basis

Docker's Engine API `PortSummary` schema requires `PrivatePort` and `Type`. `IP` and `PublicPort` are optional, and Docker's generated `PortSummary` type serializes both with `omitempty`. An absent or null `PublicPort` represents no published host port in the observed valid response and must not become a host binding.

The current StackMap decoder has two independent incompatibilities:

1. It always calls the strict string decoder for `IP`, so an omitted `IP` fails.
2. It distinguishes only `undefined` from a published `PublicPort`; `null` is passed to strict port-number validation and fails.

The adjacent container-list projection was audited against Docker's current summary, port, mount, and network-settings definitions. No additional relaxation is planned: the consumed container summary fields are emitted by Docker's summary representation; StackMap's consumed mount fields are emitted without `omitempty`; and `NetworkSettings.Networks` remains the documented attached-network source. Any implementation-time additional compatibility change requires a direct Docker API citation, focused regression coverage, and separate review rather than speculative optionality.

## Compatibility policy

1. Preserve strict validation of required `PrivatePort` and `Type` values.
2. Project omitted `IP` as no host bind address, using the existing internal empty-address representation only where needed by current mapping logic.
3. Project omitted or null `PublicPort` as unpublished, leaving internal `publicPort` absent.
4. Never manufacture a host-port mapping, exposure classification, or host-port conflict from an unpublished port.
5. Preserve current published-port projection when `IP` and `PublicPort` are present and valid.
6. Continue rejecting malformed present values, including non-string `IP`, invalid present `PublicPort`, invalid `PrivatePort`, and invalid required types.

## Acceptance criteria

- An exact port fixture `{ "PrivatePort": 2442, "PublicPort": null, "Type": "tcp" }` with omitted `IP` is accepted.
- Equivalent unpublished entries with omitted `PublicPort` and omitted `IP` are accepted.
- A container containing those entries remains present in preview.
- Unpublished ports retain their container port and protocol but have no host port and create no false host-port conflict.
- Published entries with valid `IP` and `PublicPort` preserve their current host-port mapping and exposure behavior.
- Malformed present optional values and malformed/missing required values remain rejected.
- Existing Portainer discovery, preview, selection, confirmation, explicitly confirmed create-only import, provenance, repeat-import, credential, allowlist, and HTTP/HTTPS regressions remain green.
- SQLite remains the sole authoritative inventory and provenance datastore, and the public demo remains isolated.
