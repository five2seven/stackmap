# StackMap v1.2.0 Portainer Preview Bulk-Actions Plan

**Plan status:** Ready. This plan contains one focused implementation task only.

## Objective and fixed boundary

StackMap v1.2.0 will add two explicit convenience controls to the existing Portainer import preview: selecting or clearing all importable services, and assigning one valid target host to the currently selected services. The controls operate only on the active preview's browser state. They do not discover additional data, mutate inventory, or bypass the existing acknowledgement and confirmation boundary.

SQLite remains the sole production-authoritative inventory and provenance datastore. Portainer discovery, credential and network protections, preview-token validation, explicitly confirmed create-only import, provenance, and public-demo isolation remain unchanged.

## Current implementation basis

- `PortainerImportPanel` owns the active preview, selected service IDs, per-service edits, acknowledgement, and cancellation resets.
- A new preview currently begins with no selected services. Stopped and paused services therefore remain unselected unless a user selects them.
- Services already bound by provenance are not importable and their per-service checkboxes are disabled.
- `recomputePreviewConflicts` derives host-scoped conflicts from the edited preview candidates and selected-service IDs. Bulk host assignment must update the same preview candidates used by individual target-host changes so both paths share one conflict implementation.
- Confirmation sends only the selected candidates from the displayed preview. No database write occurs before the existing explicit confirmation request succeeds.

## Interaction contract

### Select all services

1. Render one top-level checkbox with the accessible label `Select all services` while a preview is active.
2. Define the aggregate set as every importable service in that preview; provenance-bound services remain excluded and disabled.
3. Checking the control replaces the current selection with all importable service IDs, explicitly including stopped and paused containers.
4. Unchecking the control clears the selection.
5. The checkbox is checked only when every importable service is selected, unchecked when none are selected, and indeterminate when a nonempty proper subset is selected.
6. Default preview creation must not automatically select stopped or paused containers. Existing per-service selection remains available.
7. Selection state is scoped to the active preview and is cleared by the existing preview creation, cancellation, terminal-error, and successful-import resets.

### Set host for selected services

1. Render a bulk control labeled `Set host for selected services` while a preview is active.
2. Offer the valid target hosts already represented by the preview: each proposed environment host and each existing target host supplied with the preview. Values must use the same host IDs accepted by per-service controls and confirmation validation.
3. Applying a host updates `hostId` only on candidates whose IDs are currently selected. Unselected, non-importable, and absent services remain unchanged.
4. Preserve every per-service `Target host` dropdown and allow later individual changes.
5. Recompute host-scoped container-name and host-port conflicts through `recomputePreviewConflicts` after the bulk edit, exactly as for an individual host edit. Blocking conflict handling and the Import selected button remain governed by the displayed selected candidates.
6. Disable or make the bulk action inert when no services are selected or while the panel is busy. Do not apply an implicit default host choice without an explicit user action.

## Acceptance criteria

- Select all chooses every importable service in the active preview, including stopped and paused services only after that explicit bulk action.
- Clear all leaves no selected services.
- The aggregate checkbox exposes the correct checked and indeterminate states as bulk and per-service selections change.
- Provenance-bound/non-importable services are never selected by the bulk action.
- Applying a bulk host choice changes only selected candidates and supports every valid proposed or existing host available in the preview.
- Unselected candidates retain their prior host IDs.
- Host-scoped container-name and host-port conflicts appear or disappear after bulk assignment using the same logic as individual assignment.
- Per-service selection and target-host controls remain functional after any bulk action.
- Cancelling, replacing, completing, or terminally invalidating a preview clears its bulk selection state through the existing lifecycle.
- Confirmation still submits only explicitly selected candidates and remains the first point at which inventory can change.
- Existing Portainer security, discovery, token, allowlist, RFC1918 HTTP, HTTPS, redirect, confirmation, create-only import, provenance, SQLite, UI, and demo regressions remain green.

## Version and documentation impact

v1.1.3 is tagged and released. These bulk controls add a new user-facing capability rather than repairing the released PortSummary contract, so semantic versioning targets the next minor version, 1.2.0. Implementation should update version metadata, changelog, and prepared release notes only as required by repository practice. Planning, implementation, and closeout do not authorize a tag, GitHub Release, GHCR publication, Pages deployment, or announcement.

## Explicit exclusions

- Server-side bulk operations, persistent preview preferences, or state shared across previews, sessions, browsers, or refreshes.
- Automatic selection of stopped or paused containers outside an explicit Select all action.
- Selection or mutation of provenance-bound/non-importable services.
- New conflict rules or a second conflict implementation separate from `recomputePreviewConflicts`.
- Portainer discovery or projection changes; API-token lifetime/persistence; allowlisted methods/routes; response limits; RFC1918 HTTP policy; HTTPS certificate validation; redirect handling; or new outbound routes.
- Database, migration, repository, provenance, portable-backup, restore, confirmation, transaction, or create-only import changes.
- Synchronization, polling, scheduled work, refresh, update, merge, overwrite, automatic import, background behavior, Portainer/Docker mutation, or Docker socket access.
- Public-demo Portainer integration, broad UI redesign, unrelated product work, release, publication, deployment, or announcement.
