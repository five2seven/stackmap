# StackMap v1.1 Portainer API Import Plan

## Objective and authority

StackMap v1.1 adds manual Portainer API discovery followed by an explicit, reviewed import into the existing StackMap inventory. SQLite remains the sole production-authoritative datastore. Portainer is never an authority, synchronization target, or background data source.

The integration uses the existing single non-root Node.js process. The browser communicates only with same-origin StackMap APIs. The server reads one operator-configured Portainer origin from `STACKMAP_PORTAINER_URL`, accepts a user-supplied Portainer API token through the production UI, and sends that token only as an `X-API-Key` header to a fixed allowlist of read-only Portainer routes.

When `STACKMAP_PORTAINER_URL` is absent, Portainer import is disabled and its production UI entry point is unavailable. Users cannot supply or override an outbound URL. The public demo contains no Portainer UI, client, routes, configuration, or outbound integration code.

## Fixed v1.1 safety contract

- Use HTTPS with normal system certificate and hostname validation. Do not support HTTP, insecure TLS bypass, custom user-supplied destinations, redirects to another origin, or arbitrary proxy paths.
- Keep the API token only in bounded, short-lived server memory. Never persist, log, return, back up, place in a URL, or store it in browser storage. The browser receives only opaque random connection and preview tokens.
- Permit only these outbound requests, all with `GET`, `Accept: application/json`, and `X-API-Key`:
  - `/api/endpoints`
  - `/api/endpoints/{id}/docker/info`
  - `/api/endpoints/{id}/docker/version`
  - `/api/endpoints/{id}/docker/containers/json?all=true`
- Never call container inspect, stacks, registries, secrets, configs, logs, stats, events, or a caller-controlled Docker proxy path.
- Strictly project allowlisted response fields. Never read into the normalized model, import, return, log, or persist labels, environment-variable values, registry credentials, secrets, or unapproved response fields.
- Do not mount or access the Docker socket and do not call Docker hosts directly.
- Do not mutate Portainer or Docker. Do not add synchronization, polling, scheduled work, automatic discovery, automatic import, automatic refresh, overwrite, merge, or update behavior.
- Preserve the portable backup schema. A full StackMap restore will clear Portainer source/binding metadata in the same transaction as inventory replacement.
- Bind preview and confirmation to the expected StackMap inventory revision. Confirmation inserts the selected dataset and its non-secret provenance in one SQLite transaction or changes nothing.

## Approved mapping

### Environments to hosts

- Discover only supported Docker environments visible to the supplied token.
- Create at most one proposed StackMap host per selected Portainer environment unless the user explicitly attaches its containers to an existing StackMap host.
- Map the Portainer environment name, falling back to the Docker info name, to the proposed host name.
- Set host type to `container-host` and derive a concise operating-system value from allowlisted Docker info fields.
- Leave host IP blank unless an allowlisted Portainer/Docker field provides a trustworthy literal IP address. Do not treat an agent, socket, control-plane, hostname, or full URL as an IP address.
- Generate new StackMap IDs and timestamps during preview. Never derive a StackMap ID directly from an external numeric environment ID.

### Containers to services

- Discover running and stopped containers through `containers/json?all=true`; importing either requires explicit user selection.
- Normalize the first container name by removing one leading slash. Use it for both the proposed service name and container name.
- Map the image reference to `dockerImage`; leave description, application URL, internal URL, notes, and dependencies empty.
- Map running or restarting containers to `active`. Map stopped, paused, created, exited, dead, removing, or otherwise non-running containers to `paused`. Status is editable in preview.
- Map distinct Docker port tuples to StackMap ports: private port to container port, public port when present to host port, TCP/UDP directly, and unsupported protocols to `unknown` with a warning. Preserve multiple distinct bindings and allow practical per-port deselection.
- Import bind mounts only: source to host path, destination to container path, inverse of `RW` to read-only, and blank purpose. Skip named and anonymous volumes and show a warning. Allow practical per-bind-mount deselection.
- A container with exactly one network maps to that network. Zero networks map to blank. Multiple networks block confirmation for that container until the user explicitly selects one.
- Set exposure to `local` only when every published binding is loopback-only. Use `unknown` for unpublished ports, non-loopback bindings, mixed bindings, or ambiguous data. Never infer VPN, reverse proxy, or public exposure.
- Do not infer dependencies from networks, names, ports, labels, runtime order, or other heuristics.

## Duplicate and conflict policy

Phase 1 preview compares proposed records with the authoritative inventory without writing it. It reports:

- exact previously imported environment/container identities when source bindings exist;
- stale bindings whose StackMap target no longer exists;
- probable host duplicates by normalized name or trustworthy literal IP;
- probable service duplicates by normalized container name on the proposed or selected host;
- existing and within-selection host-port/protocol conflicts using StackMap's current conflict rules;
- repeated source identities or normalized duplicate candidates;
- multiple-network choices, unsupported protocols, skipped volumes, malformed fields, limits, and other lossy mappings.

Phase 2 stores non-secret source and binding metadata in SQLite using the configured Portainer origin identity, Portainer environment ID, Docker container ID, target StackMap record ID, and import timestamps. It stores no API token or discovered secret-bearing data. An already-bound container defaults to skipped and cannot overwrite, merge with, refresh, or update its existing service. The user may skip candidates, import new candidates, attach containers to an existing host, edit approved proposed fields, select one network, and deselect practical individual ports or bind mounts. Blocking conflicts require an explicit resolution before confirmation.

## Phase 2: Atomic confirmation, hardening, and release completion

- **Status:** Ready
- **Branch:** `codex/portainer-atomic-import`
- **Goal:** Add explicit atomic import of the reviewed selection, durable non-secret repeat-import metadata, restore integration, full operational hardening, and v1.1 documentation.
- **Scope:**
  - Add transactional SQLite migrations for Portainer source and host/container binding metadata with uniqueness, referential-integrity, and stale-binding behavior.
  - Keep the existing portable backup schema and exported payload unchanged; clear all Portainer source/binding metadata transactionally during a successful full restore, and retain it unchanged on every failed restore.
  - Bind previews to an expected inventory revision and an exact normalized candidate snapshot. Require explicit selected candidate IDs, all blocking resolutions, and a confirmation acknowledgement.
  - Add one repository transaction that creates only selected new hosts, services, ordered ports, selected bind mounts, and source/binding records; initializes record revisions consistently; advances the global inventory revision once; and rolls back every write on failure.
  - Permit explicit attachment to an existing host without modifying that host. Never update, overwrite, merge, or refresh an existing service.
  - Default already-bound containers to skipped and reject confirmation that attempts to import them as an overwrite.
  - Consume confirmation tokens safely; reject expired, reused, tampered, concurrent, or stale confirmations without partial writes.
  - Complete production UI confirmation/results behavior, focused E2E and container regression coverage, security hardening, operator documentation, architecture/decision records, release notes, and public demo safeguards.

## Advancement and completion

Only one phase may be implemented per feature branch and pull request. Phase 1 requires a separate read-only review of its full diff against `origin/main` and a Ready to merge recommendation before a normal merge commit. Phase 2 becomes Ready only through a separate planning-advancement branch after Phase 1 is reviewed, merged, and recorded with its implementation commits, merge commit, Entire checkpoints, validation, limitations, and datastore authority.

Phase 2 follows the same implementation, review, merge, and planning-closeout sequence. Neither phase may begin the next phase, merge its own pull request, or modify planning records directly on `main`.
