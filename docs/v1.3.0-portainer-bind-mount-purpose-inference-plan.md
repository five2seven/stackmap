# StackMap v1.3.0 Portainer Bind-Mount Purpose Inference Plan

**Plan status:** Ready. Exactly one implementation task exists and no implementation or release work is included in this planning change.

## Objective and version decision

StackMap will add conservative best-effort purpose inference for bind mounts discovered through the existing manual Portainer preview. High-confidence container-side paths will start with a useful purpose, users will see and may edit or clear that value before confirmation, and the confirmed import will persist exactly the final preview value.

Version `1.3.0` is appropriate because v1.2.1 is already released and this change adds new user-visible preview behavior and an editable Portainer control rather than repairing a regression in an already specified v1.2.x contract. No v1.3.0 release or publication is part of this task.

## Confirmed repository state

- `PathMapping.purpose` is an unconstrained string throughout the client, API, and SQLite repository rather than a closed set or enum. Normalization trims it, and blank remains valid.
- Established application-generated purpose strings are `Configuration` and `Data` from legacy path migration plus `Configuration`, `Media library`, and `Application data` in bundled sample data. Tests also demonstrate that users may enter other free-form values.
- `mapContainer()` currently projects every Portainer bind mount with `purpose: ''`, even when its container destination is semantically clear.
- The Portainer preview currently lets users include or remove a bind mount but does not show a purpose input.
- Confirmation treats selected paths as exact subsets of the original candidate paths. A client-side purpose edit would currently fail confirmation, so implementation must narrowly distinguish an allowed purpose edit from tampering with discovered mount facts.
- Confirmed import already writes the selected preview candidate through the atomic create-only SQLite transaction. No post-confirmation inference is needed or permitted.

## Fixed inference contract

Inference is deterministic, conservative, and based on the container destination because it is defined by the containerized application. The initial implementation will not inspect the administrator-controlled host source path, image name, labels, service name, or other weak signals.

For matching only, trim whitespace, treat `/` as the separator, collapse redundant separators, remove trailing separators other than the root, and compare path segments case-insensitively. Do not rewrite the original host or container path stored in the preview.

Match only the normalized terminal segment:

| Terminal segment | Inferred purpose |
| --- | --- |
| `config`, `configs`, `configuration`, `conf` | `Configuration` |
| `metadata` | `Metadata` |
| `movies`, `tv`, `music`, `audiobooks`, `books`, `photos` | `Media library` |

`Metadata` does not create a domain category: the field is already free-form text. It is the concise high-confidence description requested for a container directory explicitly named `metadata`.

The generic terminal segment `data`, including `/data`, remains blank in this first rule set. Although `Application data` is an established purpose string, `/data` is commonly used for application state, downloads, media, shared datasets, or other content and is not sufficiently specific. Partial names such as `myconfig`, `metadata-cache`, or `movies-old` also remain blank. Unmatched, relative, malformed, root, Windows-style, or otherwise ambiguous destinations remain blank. Host paths alone never cause inference.

## Preview editing and confirmation boundary

1. Server preview construction assigns the inferred purpose once to each accepted bind-mount candidate.
2. The preview renders an accessible purpose text input for each included bind mount alongside its host/container paths and access mode. The inferred value is visible before selection confirmation.
3. Users may replace the inferred text or clear it. Removing a bind mount from the preview retains existing include/remove semantics.
4. Client state sends the final purpose with the selected service. It does not rerun inference.
5. Server confirmation identifies every selected path by its original preview ID, requires it to be a subset of the offered paths, and requires host path, container path, and read-only state to remain exact. Only `purpose` may differ.
6. The final purpose must remain a string and pass the existing path/service validation and size rules. Unknown keys, duplicate IDs, unoffered paths, non-string purposes, or changes to discovered mount facts fail closed without inventory or provenance mutation.
7. The existing repository transaction imports the accepted final purpose. Inference is never reapplied during or after the transaction.

This is still preview-only state until explicit acknowledgement and confirmation. SQLite remains authoritative, and existing expected-revision, preview-token, stale/live binding, and rollback protections remain unchanged.

## Warning wording decision

The current warning is not a general complaint that a path purpose is blank. `hasConfigurationPath()` specifically checks whether at least one purpose contains `config`, and both service completeness and Path Map warnings use that result. The meaning remains useful, but `No configuration-purpose mapping recorded.` sounds as though the broader free-form purpose field is configuration-only.

The planned user-facing replacement is `No path is marked for configuration.` It describes the actual predicate in plain language without changing when the warning appears. Focused domain, service-card, and Path Map tests must lock that semantic boundary. No broader missing-purpose warning is added.

## Planned implementation scope

Likely implementation files are limited to:

- `server/portainer.ts` for the pure container-path inference helper, preview projection, and narrow purpose-edit confirmation validation.
- `server/portainer.test.ts` for inference, normalization, ambiguity, response projection, and confirmation tamper cases.
- `server/portainer-api.test.ts` and/or `server/portainer-import.test.ts` for persisted override/clear values and atomic lifecycle regression.
- `src/components/PortainerImportPanel.tsx` and its focused component tests for visible, editable, clearable per-bind-mount purposes while retaining include/remove behavior.
- `src/App.tsx`, `src/components/PathMapView.tsx`, and focused warning tests only for the approved wording replacement with unchanged predicate semantics.
- Version metadata, changelog, README, health assertions, and prepared release notes only as required for the established v1.3.0 implementation workflow.

No database migration or backup-format change is expected because purposes are already persisted as strings.

## Acceptance criteria

- `/config`, `/app/config/`, mixed-case equivalents, and the other exact configuration terminal segments infer `Configuration`.
- `/metadata` and normalized exact terminal equivalents infer `Metadata`.
- `/movies`, `/tv`, `/music`, `/audiobooks`, `/books`, and `/photos`, including normalized nested terminal equivalents, infer `Media library`.
- `/data`, host-only semantic names, partial-name matches, and every ambiguous/unmatched destination remain blank.
- The original source and destination strings remain unchanged by classification.
- The preview visibly exposes each purpose and permits editing and clearing it.
- A confirmed override and a confirmed cleared value are persisted exactly; confirmation does not recompute or restore the inferred value.
- A tampered host path, container path, access flag, path identity, extra path, invalid purpose type, or unknown shape is rejected without mutation.
- The warning reads `No path is marked for configuration.` and retains the existing configuration-specific behavior.
- Existing create-only import, explicit confirmation, expected revision, atomic rollback, stale/live provenance, bulk selection, host assignment/intersection, conflict, Portainer security, SQLite, backup/restore, and demo behavior remains unchanged.

- Existing live-binding rejection, stale-binding reattachment, repeat-import protection, provenance, and rollback remain unchanged.
- Existing individual/select-all selection, stopped/paused defaults, selected-only host assignment, host-choice intersection, cross-environment proposed-host restriction, and conflict recomputation remain unchanged.
