# StackMap v1.1.2 Portainer Environment Compatibility Plan

**Plan status:** Ready. This plan contains one patch implementation task only.

## Objective and fixed boundary

StackMap v1.1.2 will correct Portainer environment detection for a real local Docker endpoint that reports `Type: 1` with an empty `ContainerEngine`. Portainer endpoint type semantics, rather than endpoint name, URL, or other arbitrary fields, provide the compatibility signal. Explicit `ContainerEngine: docker` support remains intact.

SQLite remains the sole production authority. The existing manual, read-only discovery and explicitly confirmed create-only import workflow remains unchanged, including provenance and all credential and network protections.

## Compatibility policy

1. Treat Portainer endpoint type 1 as Docker-compatible even when `ContainerEngine` is blank.
2. Continue treating an explicitly reported Docker container engine case-insensitively as Docker-compatible; reject it by type only when the endpoint type clearly identifies a non-Docker environment.
3. Reject blank-engine endpoints of every other type and clearly unsupported or non-Docker endpoint types even if unrelated fields resemble a Docker environment.
4. Do not infer Docker compatibility from `Name`, `URL`, `Status`, or other arbitrary endpoint fields.
5. Project the endpoint `Type` for this compatibility decision and treat an omitted optional `PublicURL` as empty, as in the exact real-world response. Preserve strict validation of required fields, limits, errors, and the behavior of downstream environment selection, discovery, preview, confirmation, and import.

## Planned implementation scope

Likely application files:

- The server Portainer endpoint projection/filtering module that currently checks only `ContainerEngine`.
- Its focused unit/integration test file and Portainer endpoint fixtures.
- Version and release-readiness files required by established patch-release practice.

No database, repository, backup/restore, provenance, network-policy, API-token, route-allowlist, UI-flow, or demo-runtime change is planned.

## Acceptance criteria

- The exact reported endpoint response with `Id: 1`, `Name: local`, `Type: 1`, blank `ContainerEngine`, `URL: unix:///var/run/docker.sock`, and `Status: 1` is retained as a regression fixture and is accepted.
- An endpoint that explicitly reports `ContainerEngine: docker` remains accepted unless its endpoint type clearly identifies a non-Docker environment.
- Unsupported and non-Docker endpoint types are rejected, including cases whose arbitrary name or URL might otherwise look Docker-related.
- Existing discovery and explicitly confirmed create-only import behavior passes unchanged.
- API tokens remain short-lived and server-memory-only; the fixed GET allowlist, redirect rejection, response limits, strict projection, and HTTP/HTTPS destination policy remain unchanged.
- SQLite remains the sole authoritative inventory and provenance datastore, with no schema or portable-backup change.
- No UI redesign, synchronization, polling, update, refresh, background job, Docker/Portainer mutation, or public-demo integration is introduced.

## Required validation

### Focused coverage

- Type 1 plus blank `ContainerEngine` is accepted using the exact real-world response fixture.
- Explicit Docker `ContainerEngine` is accepted for supported endpoint types.
- Clearly unsupported and non-Docker endpoint types are rejected.
- Existing discovery, preview, confirmation, import selection, create-only mutation, provenance, credential, and network-policy regression coverage remains green.

### Full validation

Run `npm run lint`, `npm test`, `npm run build`, `npm run test:e2e`, `npm run build:demo`, `npm run test:e2e:demo`, `npm audit --omit=dev`, and `git diff --check`. Run the Linux/amd64 container workflow and applicable Docker deployment/Portainer fixture validation. Exact-head GitHub Actions and Semgrep must pass before merge.

## Version and documentation impact

Because v1.1.1 is already tagged and released, the implementation targets patch version 1.1.2. The implementation branch should update `package.json`, the root package entries in `package-lock.json`, `CHANGELOG.md`, and `docs/release-notes.md` as required for a patch release. Public/operator documentation should change only if the compatibility rule needs explanation beyond release notes. Do not tag, create a GitHub Release, publish GHCR, deploy Pages, or announce the release in planning or implementation.

## Explicit exclusions

- Authentication, accounts, telemetry, external persistence, or Docker socket access.
- Changes to API-token lifetime or persistence, allowlisted methods/routes, redirect handling, response projection, or secret exclusions.
- Changes to the private-LAN HTTP policy, HTTPS certificate validation, TLS controls, or outbound Portainer origin configuration.
- Database schema, provenance schema or semantics, portable-backup schema, restore behavior, mapping, confirmation, or transaction changes.
- UI workflow redesign; synchronization, polling, scheduled work, automatic discovery/import/refresh, update, merge, or overwrite behavior.
- Portainer or Docker mutation, public-demo Portainer integration, or unrelated product work.
- Version tag, GitHub Release, GHCR publication, Cloudflare Pages deployment, or announcement.

Planning closeout and any release operations remain separate later tasks. No additional v1.1.2 product task is defined by this plan.
