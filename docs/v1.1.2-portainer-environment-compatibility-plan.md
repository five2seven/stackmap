# StackMap v1.1.2 Portainer Environment Compatibility Plan

**Plan status:** Complete. The single patch implementation task is Complete; no additional task exists. This closeout does not tag or release v1.1.2, publish GHCR, or deploy Pages.

## Objective and fixed boundary

StackMap v1.1.2 will correct Portainer environment detection for a real local Docker endpoint that reports `Type: 1` with an empty `ContainerEngine`. Portainer endpoint type semantics, rather than endpoint name, URL, or other arbitrary fields, provide the compatibility signal. Explicit `ContainerEngine: docker` support remains intact.

SQLite remains the sole production authority. The existing manual, read-only discovery and explicitly confirmed create-only import workflow remains unchanged, including provenance and all credential and network protections.

## Compatibility policy

1. Treat Portainer endpoint type 1 as Docker-compatible even when `ContainerEngine` is blank.
2. Continue treating an explicitly reported Docker container engine case-insensitively as Docker-compatible; reject it by type only when the endpoint type clearly identifies a non-Docker environment.
3. Reject blank-engine endpoints of every other type and clearly unsupported or non-Docker endpoint types even if unrelated fields resemble a Docker environment.
4. Do not infer Docker compatibility from `Name`, `URL`, `Status`, or other arbitrary endpoint fields.
5. Project the endpoint `Type` for this compatibility decision and treat an omitted optional `PublicURL` as empty, as in the exact real-world response. Preserve strict validation of required fields, limits, errors, and the behavior of downstream environment selection, discovery, preview, confirmation, and import.

## Acceptance criteria

- The exact reported endpoint response with `Id: 1`, `Name: local`, `Type: 1`, blank `ContainerEngine`, `URL: unix:///var/run/docker.sock`, and `Status: 1` is retained as a regression fixture and is accepted.
- An endpoint that explicitly reports `ContainerEngine: docker` remains accepted unless its endpoint type clearly identifies a non-Docker environment.
- Unsupported and non-Docker endpoint types are rejected, including cases whose arbitrary name or URL might otherwise look Docker-related.
- Existing discovery and explicitly confirmed create-only import behavior passes unchanged.
- API tokens remain short-lived and server-memory-only; the fixed GET allowlist, redirect rejection, response limits, strict projection, and HTTP/HTTPS destination policy remain unchanged.
- SQLite remains the sole authoritative inventory and provenance datastore, with no schema or portable-backup change.
- No UI redesign, synchronization, polling, update, refresh, background job, Docker/Portainer mutation, or public-demo integration is introduced.
