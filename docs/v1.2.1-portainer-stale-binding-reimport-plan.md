# StackMap v1.2.1 Portainer Stale-Binding Re-import Plan

**Plan status:** Complete. The single implementation task is Complete; no additional task exists. This closeout does not tag or release v1.2.1, publish GHCR, or deploy Pages.

## Objective and fixed boundary

StackMap v1.2.1 will restore intentional Portainer re-import after a previously imported StackMap service is manually deleted. A binding whose target service still exists remains protected. A preserved binding whose target was deleted becomes eligible for preview and may be attached to a newly created service only by the existing explicitly confirmed, expected-revision-checked, atomic import transaction.

SQLite remains the sole production-authoritative inventory and provenance datastore. This is a compatibility and UX repair to released v1.2.0 behavior, not synchronization, overwrite, update, or automatic cleanup.

## Confirmed root cause

- `portainer_container_bindings.service_id` uses `ON DELETE SET NULL`, intentionally preserving source/environment/container history after a service is deleted.
- `portainerBindings()` retains that row and omits `serviceId` when the database value is null.
- Preview mapping currently sets `alreadyBound` from source/environment/container row existence alone. It therefore adds the blocking `ALREADY_BOUND` conflict even when the preserved row no longer targets a service.
- Repository confirmation currently rejects any matching container-binding row before service creation, also without distinguishing a live target from a null stale target. Merely changing the preview would therefore still fail atomically with `PORTAINER_ALREADY_BOUND`.
- With every candidate misclassified as non-importable, bulk selection has no eligible IDs and bulk host assignment has no selected candidate to update. Current UI code already guards the aggregate checked state with a nonempty eligible-set check and disables host application at zero selections; focused browser regression coverage is still required for the reported production state.

## Binding and transaction contract

1. A live binding is a source/environment/container row whose `service_id` points to an existing service. Preview continues to mark it already bound, confirmation continues to reject it, and Select all continues to exclude it.
2. A stale binding is the preserved row whose target service was deleted and whose `service_id` is null. Preview treats its container as importable and does not attach the live-binding blocking message.
3. Confirmed import creates a new service through the existing create-only path, then atomically updates only that matching stale row to the new service ID and current import timestamp. The transaction must fail unless the row is still stale; a concurrent or tampered live binding remains `PORTAINER_ALREADY_BOUND`.
4. A container with no prior binding continues to use the normal binding insertion path. No provenance row is erased merely to permit re-import.
5. Expected inventory revision, host existence, service validation, child creation, revision increment, rollback behavior, and all-or-nothing provenance writes remain unchanged.
6. After success, repository snapshots expose the new service binding and the next preview again applies normal repeat-import protection.

## Preview and bulk-control contract

- A stale candidate is eligible for the same individual and bulk controls as a never-imported candidate. It may optionally receive a concise non-blocking explanation that its prior StackMap service was deleted.
- The message `This container was imported previously and is skipped by default.` is reserved for a live binding.
- `Select all services` derives checked and indeterminate state only from actually importable candidates. An empty eligible set is unchecked and non-indeterminate; none/some/all behavior remains correct for nonempty sets.
- The bulk host action remains disabled or unavailable when no eligible candidate is selected.
- Once a stale candidate is selected, applying an existing host updates that selected preview candidate normally. Selected-only mutation, intersection of host choices valid for all selected services, same-environment proposed hosts, cross-environment proposed-host exclusion, and host-scoped conflict recomputation retain v1.2.0 semantics.
- All edits remain active-preview browser state until explicit acknowledgement and confirmation.

## Acceptance criteria

- Importing and then deleting a StackMap service leaves preserved provenance but makes its live Portainer container importable in a fresh preview.
- The stale candidate is selectable, accepts an existing target host, passes server confirmation, creates a new service, and becomes bound to that new service in the same transaction.
- A subsequent preview skips the container again because its replacement target exists.
- Existing live bindings remain protected in preview and confirmation; deliberately tampered or concurrent attempts cannot replace them.
- Stale bindings do not display the live-binding blocking message.
- Zero eligible candidates renders Select all unchecked and non-indeterminate and prevents host application; partial and complete eligible selections remain accurate.
- Existing v1.2.0 bulk host choices, cross-environment restrictions, selected-only updates, conflict recomputation, individual controls, and final confirmation payloads remain correct.
- No inventory or provenance mutation occurs before explicit confirmation, and failed imports leave both unchanged.
